# CallGear CRM App Product Logic

_Актуальная версия документа. Основано на текущем коде в `src/app.js` и `src/styles.css` на 2026-06-17._

## 1. Цель документа

Этот документ фиксирует продуктовую логику приложения для разработчика:

- какие разделы и маршруты существуют;
- какие глобальные состояния влияют на приложение;
- как работает навигация и рендер;
- какие feature flags и системные переключатели меняют состав экранов;
- где и как хранится пользовательское состояние.

Документ собран как цельное описание текущей логики приложения. Разделы идут от глобального каркаса к данным, экранной логике и межэкранным зависимостям.

### 1.1. Словарь терминов

Чтобы текст читался единообразно, в документе используются следующие термины:

- `маршрут` — hash-маршрут приложения, например `#/clients` или `#/task/:id`;
- `экран` — самостоятельное пользовательское представление внутри маршрута;
- `состояние` — данные, которые влияют на поведение интерфейса и хранятся в памяти, `localStorage` или query-параметрах;
- `feature-флаг` — системный переключатель, который меняет состав экранов или доступность функций;
- `производная модель` — объект, который не хранится отдельно, а собирается из seed-данных, пользовательских правок и вычислений;
- `пустое состояние` — сценарий, в котором раздел не содержит данных и показывает специальный UI;
- `CTA` — основное целевое действие на экране, обычно кнопка следующего шага;
- `detail-экран` — детальный экран конкретной сущности: клиента, задачи, касания или чата;
- `read-only` — экран без редактирования данных напрямую;
- `side effect` — дополнительное последствие действия, которое меняет соседние данные, навигацию или состав интерфейса.

## 4. Глобальные feature flags и режимы

### 4.1. Язык интерфейса

Источник: `settings.interfaceLanguage`.

Поддерживаемые значения:

- `english`
- `russian`

Фактическая локаль вычисляется через `getCurrentLocale()`:

- `english` -> `en`
- все остальное допустимое -> `ru`

В режиме `en` приложение:

- меняет `document.documentElement.lang`;
- прогоняет весь отрендеренный DOM через `localizeElementTree(app)`;
- переводит текстовые узлы, `aria-label`, `placeholder`, `title`;
- использует `englishTextMap` и набор динамических date/string replacements.

Важно: локализация выполняется постфактум над уже отрендеренным DOM. Это влияет на требования к будущим изменениям:

- любая новая строка должна либо сразу генерироваться через `translateText`, либо быть совместима с DOM-локализацией;
- пользовательские строки и динамические шаблоны нужно добавлять в `englishTextMap` или в динамические replacement-правила.

### 4.2. RMO features

Источник: `settings.rmoFeaturesEnabled`.

По умолчанию: `false`.

Когда `rmoFeaturesEnabled = false`:

- маршруты `calls`, `chats`, `chat`, `dialer` недоступны;
- при прямом переходе на них происходит редирект на `#/clients`;
- экран `settings-account` недоступен и редиректит на `#/settings-preferences`;
- route `settings` рендерит сразу `renderSettingsPreferencesApp()`, минуя промежуточный экран аккаунта;
- в каталоге контактов скрывается вкладка `Сотрудники`;
- нижний tab bar работает в режиме `search-trailing`, где поиск вынесен в отдельную кнопку справа.

Когда `rmoFeaturesEnabled = true`:

- звонки и чаты доступны;
- `settings` рендерит полноценный экран настроек;
- вкладка `Сотрудники` возвращается;
- tab bar использует основной продуктовый набор вкладок.

### 4.3. Root splash

Глобальный splash показывается только если `window.location.hash` пустой и `isRootSplashVisible = true`.

Особенности:

- splash живет `5000ms`;
- таймер создается через `ensureRootSplashTimer()`;
- после истечения времени вызывается полный `render()`.

## 5. Глобальная навигация и рендер-пайплайн

### 5.1. Главный render loop

Все приложение рендерится одной функцией `render()`.

Общий порядок:

1. Определить `route` и `routeParam`.
2. Прочитать auth state.
3. Прочитать `rmoFeaturesEnabled`.
4. Проверить глобальные редиректы и ограничения.
5. Сгенерировать HTML нужной страницы.
6. Вставить HTML в `#app`.
7. Синхронизировать пустой viewport lock.
8. Привязать события через `bindAppEvents(route, routeParam)`.
9. Для `ui-library` дополнительно вызвать `bindStorybookPage`.
10. Запустить локализацию через `localizeApp()`.

### 5.2. Глобальные редиректы

До рендера действуют следующие правила:

- если route отсутствует и splash уже скрыт -> показать `onboarding`;
- если route = `setup` и пользователь уже авторизован -> редирект на `#/clients`;
- если RMO выключен и route в `calls/chats/chat/dialer` -> редирект на `#/clients`;
- если RMO выключен и route = `settings-account` -> редирект на `#/settings-preferences`;
- если route соответствует legacy component-route (`colors`, `button`, `row` и т.д.) -> редирект в `#/ui-library/<page>`.

### 5.3. Навигационная архитектура

В приложении одновременно существуют:

- навигация на уровне маршрутов через `window.location.hash`;
- history-back кнопки;
- внутренние ссылки в header/button/row;
- modal и sheet состояния, управляемые через DOM и local state;
- фильтры и storybook controls, которые пишут значения в `window.location.search`.

Поисковый экран строит `back`-ссылку на основе текущего hash через `getSearchHref()`.

## 6. Глобальные auth и permission-механики

### 6.1. Auth state

`auth` хранится в `callgear.auth`.

На глобальном уровне он используется для:

- определения авторизован ли пользователь;
- сохранения прогресса setup;
- хранения `setupPermissions`;
- хранения `permissionPrompts`.

### 6.2. Auth flow state

`authFlow` хранится отдельно в `callgear.authFlow`.

Он нужен для временных данных auth-сценария:

- номер в регистрации;
- номер в восстановлении;
- промежуточные шаги, которые не должны жить в постоянном auth state.

### 6.3. Setup permissions и permission prompts

Базовые разрешения:

- `calls`
- `chats`
- `notifications`
- `contacts`

Базовые post-login prompt flags:

- `notifications`
- `contacts`
- `whatsapp`

Порядок модалок после логина жестко задан массивом `postLoginPermissionOrder`:

1. `notifications`
2. `contacts`
3. `whatsapp`

`getPostLoginPermissionStep()` возвращает первый неотмеченный prompt, поэтому одновременно в приложении может показываться только одна post-login permission modal.

## 7. Глобальные UI-механики

### 7.1. Пустые состояния

Для части экранов предусмотрен отдельный viewport lock через `syncEmptyViewportLock()`.

Это влияет на композицию пустых экранов:

- они могут вести себя иначе по высоте;
- часть пустых экранов имеет отдельные иллюстрации, нижний tab bar и centered layout.

### 7.2. Сегменты

`renderSegmentedControl()` — единая точка генерации сегментов.

Поддерживаемые варианты:

- `pill`
- `topline`
- `large`

Scroll-поведение:

- для pill/large/topline в ряде экранов сегменты могут переходить в горизонтальный скролл;
- swipe between segments поддерживается через `bindSegmentedControlSwipe`;
- для `pill + scroll` добавлен отдельный визуальный scroll hint справа и слева;
- scroll hint должен применяться везде, где используется общий компонент и включен `scroll`.

Типографика:

- у варианта `topline` текстовый label использует caption-типографику.

### 7.3. UI-модели наложений

В приложении используются несколько типов наложений:

- alert modal;
- bottom sheet;
- glass menu;
- picker modal;
- analysis modal;
- post-login permission modal.

Для разработчика это означает:

- один и тот же экран может существовать в нескольких слоях состояния;
- визуальное состояние страницы не всегда выражено только маршрутом;
- значимая часть логики скрыта в bind-функциях после рендера.

## 11. Старт приложения

### 11.1. Первый экран при открытии приложения

Если `window.location.hash` пустой, приложение идет по двум последовательным экранам:

1. root splash;
2. onboarding.

Логика такая:

- при пустом hash и `isRootSplashVisible = true` рендерится splash;
- splash показывается `5000ms`;
- после завершения таймера вызывается `render()`;
- при следующем проходе, если route все еще отсутствует, рендерится onboarding.

### 11.2. Splash

Splash не имеет пользовательских действий и не хранит дополнительное состояние.

Он выполняет только две функции:

- визуальный вход в приложение;
- пауза перед показом онбординга.

## 12. Онбординг

### 12.1. Структура

Онбординг состоит из 3 слайдов. Текущий шаг определяется query-параметром `step` в hash-маршруте `#/onboarding?step=N`.

Шаг нормализуется функцией `getOnboardingStepFromUrl()`:

- если `step` отсутствует, используется `1`;
- если `step < 1`, берется `1`;
- если `step > 3`, берется `3`.

### 12.2. Контент слайдов

#### Слайд 1

- Заголовок:
  - `Все данные по клиенту`
  - `в одном месте`
- Описание:
  - `Задачи, актуальная информация и история общения по каждому клиенту собираются в одной карточке`

#### Слайд 2

- Заголовок:
  - `Обновление после`
  - `каждого разговора`
- Описание:
  - `AI-помощник сохраняет главное, обновляет данные и фиксирует договоренности`

#### Слайд 3

- Заголовок:
  - `Уведомления`
  - `о важном`
- Описание:
  - `Ежедневные уведомления о срочных задачах и клиентах, которые требуют внимания в первую очередь`

### 12.3. Поведение CTA

На каждом слайде есть:

- pagination dots;
- primary CTA;
- secondary link `Пропустить`.

Primary CTA работает так:

- на шагах 1 и 2 кнопка имеет текст `Далее`;
- на шаге 3 кнопка имеет текст `Начать работу`;
- на шагах 1 и 2 переход идет на следующий `step`;
- на шаге 3 переход идет на `#/login`.

Ссылка `Пропустить` на всех шагах ведет сразу на `#/login`.

### 12.4. Состояние завершения онбординга

Отдельный флаг завершения онбординга не сохраняется.

Текущее поведение приложения такое:

- онбординг показывается как маршрут по умолчанию после splash;
- дальнейший путь пользователя определяется уже через переход на `#/login`;
- при прямом открытии другого hash-route онбординг обходится.

## 13. Экран логина и auth routing

### 13.1. Поддерживаемые режимы

Экран `#/login` работает в трех режимах:

- `signin`
- `register`
- `recovery`

Режим задается query-параметром `mode`.

Допустимые значения:

- `signin`
- `register`
- `recovery`

Любое другое значение приводится к `signin`.

### 13.2. Поддерживаемые шаги

Шаг зависит от режима.

Для `signin` допустим только:

- `signin`

Для `register`:

- `phone`
- `code`
- `password`

Для `recovery`:

- `phone`
- `code`
- `password`

Если шаг невалиден для режима, приложение заменяет его на первый допустимый шаг этого режима.

### 13.3. Отдельная особенность code-step

Для `register` и `recovery` маршрут `step=code` существует как route-state, но визуально код вводится не на отдельной странице, а в нижней шторке.

Это устроено так:

- route остается `#/login?mode=<mode>&step=code`;
- базовая страница рендерится как phone-step;
- поверх нее показывается `cg-auth-code-modal`.

Фактически:

- `showCodeSheet = true`, если `mode` равен `register` или `recovery` и `step = code`;
- `effectiveStep` в этом случае становится `phone`.

Для разработчика это важно, потому что:

- DOM phone-step и code sheet живут одновременно;
- submit основной формы и submit шторки имеют разную роль;
- ошибки по коду показываются внутри шторки.

## 14. Вход

### 14.1. Состав экрана

Экран входа содержит:

- иллюстрацию `illustrationAssets.login`;
- заголовок `Войти`;
- поле `Логин`;
- поле `Пароль`;
- primary CTA `Войти`;
- secondary CTA `Зарегистрироваться`.

### 14.2. Обязательные поля

Для активации кнопки `Войти` должны быть заполнены:

- `username`
- `password`

Поля считаются заполненными после `trim()`.

### 14.3. Проверка логина

В текущей демо-логике валидная пара только одна:

- логин: `admin`
- пароль: `admin`

Если пара совпала:

- в `callgear.auth` записывается новый auth state;
- пользователь считается авторизованным;
- происходит переход на `#/clients`.

Если пара не совпала:

- показывается ошибка `Неправильный логин или пароль`.

### 14.4. Что сохраняется при успешном входе

При успешном входе через `signin` сохраняется:

- `isAuthenticated: true`
- `username`
- `loggedInAt`
- `setupCompleted: true`
- `setupPermissions`
- `permissionPrompts`

Начальные значения разрешений после такого входа:

- `setupPermissions.calls = false`
- `setupPermissions.chats = false`
- `setupPermissions.notifications = false`
- `setupPermissions.contacts = false`

Начальные значения post-login prompt flags:

- `permissionPrompts.notifications = false`
- `permissionPrompts.contacts = false`
- `permissionPrompts.whatsapp = false`

Важно: обычный логин сразу помечает `setupCompleted: true`, поэтому route `#/setup/*` после входа больше не используется.

## 15. Регистрация

### 15.1. Шаг 1. Ввод номера

Route:

- `#/login?mode=register&step=phone`

Состав экрана:

- иллюстрация `illustrationAssets.signUp`;
- заголовок `Регистрация`;
- поле `Введите номер телефона CallGear`;
- helper-текст:
  - `Если нет номера, его нужно`
  - ссылка `приобрести отдельно` на [https://callgear.com/](https://callgear.com/)
- primary CTA `Получить код`;
- secondary CTA `Назад ко входу`.

### 15.2. Обязательность и валидация номера

Кнопка `Получить код` становится активной, когда в номере не меньше 6 цифр.

Проверка делается по digits-only значению.

Дополнительно применяется нормализация:

- удаляются недопустимые символы;
- сохраняются только разрешенные символы телефона;
- лишние `+` внутри строки удаляются.

Если пользователь отправляет форму с номером короче 6 цифр:

- показывается ошибка `Введите номер телефона`.

### 15.3. Что происходит после успешной отправки номера

После успешного submit:

- нормализованный номер сохраняется в `callgear.authFlow.registerPhone`;
- приложение переходит на `#/login?mode=register&step=code`.

### 15.4. Защита от пропуска шага телефона

Если пользователь открыл:

- `#/login?mode=register&step=code`
- `#/login?mode=register&step=password`

и при этом `registerPhone` отсутствует в `authFlow`, приложение автоматически возвращает его на:

- `#/login?mode=register&step=phone`

### 15.5. Шаг 2. Ввод кода

Код вводится в нижней шторке поверх phone-step.

Состав шторки:

- заголовок `Введите код из SMS`;
- 6 отдельных ячеек ввода;
- primary CTA `Подтвердить код`;
- secondary CTA для повторной отправки кода.

### 15.6. Логика code input

Код шестизначный.

Механика ввода:

- каждая ячейка принимает только одну цифру;
- после ввода фокус автоматически переходит в следующую ячейку;
- `Backspace` на пустой ячейке переводит фокус назад;
- при focus значение выделяется;
- поддерживается paste:
  - берутся только цифры;
  - длина ограничивается 6 символами;
  - цифры раскладываются по всем слотам.

Hidden value собирается из всех 6 слотов.

Кнопка `Подтвердить код` активна, только когда заполнены все 6 символов.

### 15.7. Верный код

Текущий demo-code жестко задан:

- `123456`

### 15.8. Ошибки на шаге кода

Если код введен не полностью:

- ошибка `Введите код полностью`

Если код не совпадает с `123456`:

- ошибка `Неверный код`

### 15.9. Повторная отправка кода

Кнопка повтора сначала выключена.

Стартовое состояние:

- `Отправить код еще раз через 00:59`
- `disabled = true`

Поведение:

- таймер убывает каждую секунду;
- после достижения `00:00` кнопка становится активной;
- текст меняется на `Отправить код еще раз`;
- при нажатии на активную кнопку:
  - все 6 ячеек очищаются;
  - ошибка скрывается;
  - фокус возвращается в первую ячейку;
  - таймер перезапускается снова с `00:59`.

### 15.10. Закрытие шторки кода

Закрытие по scrim или кнопке закрытия:

- не отменяет регистрацию;
- возвращает пользователя на `#/login?mode=register&step=phone`.

Телефон при этом остается сохраненным в `authFlow`.

### 15.11. Шаг 3. Создание пароля

Route:

- `#/login?mode=register&step=password`

Состав экрана:

- заголовок `Придумайте пароль`;
- поля:
  - `Новый пароль`
  - `Повторите пароль`
- primary CTA `Сохранить пароль`;
- secondary CTA `Назад ко входу`.

### 15.12. Валидация пароля

Для активации кнопки на уровне UI должны быть непустыми оба поля:

- `password`
- `passwordConfirm`

Финальная submit-валидация:

- пароль должен быть длиной минимум 4 символа;
- оба значения должны совпадать.

Ошибки:

- `Пароль должен быть не короче 4 символов`
- `Пароли не совпадают`

### 15.13. Завершение регистрации

После успешного сохранения пароля:

- временное состояние auth flow очищается через `resetAuthFlowState()`;
- приложение уходит на `#/login?notice=password-reset`.

Отдельного auto-login после регистрации нет.

### 15.14. Success-state после регистрации

На странице логина при `notice=password-reset` показывается success modal:

- заголовок `Новый пароль сохранен`
- текст `Используйте его для входа`
- кнопка `Понятно`

Закрытие модалки:

- убирает ее из DOM;
- переводит пользователя в чистый `#/login`.

## 17. Первичная настройка (`setup`)

### 17.1. Назначение

`setup` — отдельный последовательный сценарий из 4 шагов, который описывает подключение основных источников данных и разрешений.

Маршрут:

- `#/setup/1`
- `#/setup/2`
- `#/setup/3`
- `#/setup/4`

Номер шага нормализуется в диапазон от 1 до 4.

### 17.2. Ограничение доступа

Если пользователь уже авторизован, route `#/setup/*` сразу редиректит на:

- `#/clients`

Это означает, что setup задуман как отдельный pre-product flow, а не как повторяемый раздел настроек.

### 17.3. Общая структура каждого шага

На каждом шаге есть:

- `eyebrow` вида `Шаг N из 4`;
- progress dots;
- большая иконка;
- заголовок из двух строк;
- описание;
- список benefits;
- primary CTA;
- secondary CTA;
- permission modal по primary CTA.

### 17.4. Шаг 1. Звонки

- id: `calls`
- eyebrow: `Шаг 1 из 4`
- title:
  - `Подключите`
  - `звонки`
- primary CTA: `Подключить звонки`
- secondary CTA: `Позже`
- modal title: `Разрешить доступ к звонкам?`

Benefit items:

- `Фиксация звонков по клиентам`
- `Анализ речи и summary после разговора`
- `Автоматическое обновление задач`

### 17.5. Шаг 2. Чаты

- eyebrow: `Шаг 2 из 4`

  - `Подключите`
  - `чаты`

- modal title: `Разрешить доступ к чатам?`

Benefit items:

  - `Включите`

### 17.8. Поведение secondary CTA

Secondary CTA на любом setup-шаге:

- не открывает modal;
- не сохраняет permission;
- сразу переводит на следующий шаг.

Исключение только в тексте:

- на шагах 1-3 это `Позже`;
- на шаге 4 это `Пропустить`.

### 17.9. Поведение primary CTA и modal

По нажатию primary CTA:

- открывается permission modal;
- сам переход на следующий шаг до подтверждения не происходит.

В modal есть:

- secondary action `Не сейчас`
- confirm action `Разрешить`

Если пользователь нажал `Не сейчас` или закрыл modal по клику в overlay:

- modal закрывается;
- текущий setup-шаг остается тем же;
- next step автоматически не открывается.

Если пользователь нажал `Разрешить`:

- в `auth.setupPermissions[step.id]` сохраняется `true`;
- modal закрывается;
- приложение переходит на следующий setup-шаг.

### 17.10. Завершение setup

Когда пользователь доходит до конца сценария:

- после последнего перехода вызывается `saveSetupProgress({ setupCompleted: true })`;
- приложение уходит на `#/clients`.

При этом:

- уже сохраненные разрешения не сбрасываются;
- неразрешенные шаги остаются `false`.

## 18. Post-login permission prompts

### 18.1. Когда они показываются

После авторизации поверх обычных продуктовых экранов может показываться дополнительная alert-modal с разрешением.

Она рендерится только если одновременно выполнены условия:

- пользователь авторизован;
- есть хотя бы один неотмеченный prompt в `permissionPrompts`;
- текущий route не входит в список исключений:
  - `login`
  - `onboarding`
  - `ui-library`
  - `setup`

### 18.2. Какие именно разрешения повторно запрашиваются

Повторно запрашиваются только:

- `notifications`
- `contacts`
- `whatsapp`

`calls` и `chats` в post-login prompt sequence не участвуют.

### 18.3. Порядок показа

Порядок жестко задан:

1. `notifications`
2. `contacts`
3. `whatsapp`

Пока не завершен первый prompt, второй не показывается.

### 18.4. Действия в modal

В modal две кнопки:

- `Позже`
- `Разрешить`

Поведение одинаковое по структуре:

- в `permissionPrompts[stepId]` ставится `true`;
- в `setupCompleted` дополнительно пишется `true`;
- приложение делает `render()`.

Если нажата `Разрешить`, дополнительно:

- в `setupPermissions[stepId]` записывается `true`.

Если нажато `Позже` или клик по overlay:

- разрешение в `setupPermissions` не выставляется;
- prompt считается уже показанным и больше автоматически не появится.

### 18.5. Практический смысл этой логики

С точки зрения продукта это означает:

- prompt имеет одноразовую природу;
- отказ не вызывает бесконечный повтор;
- пользователь может продолжить работу без разрешения;
- состояние `prompt shown` и состояние `permission granted` разделены.

## 19. Локальные состояния и зависимости внутри auth-flow

### 19.1. Разделение `auth` и `authFlow`

Временные данные сценария хранятся отдельно от постоянной авторизации.

`authFlow` используется для:

- номера регистрации;
- номера восстановления;
- защиты от прямого открытия следующих шагов без телефона.

`auth` используется для:

- признака входа;
- setup-флагов;
- разрешений;
- post-login prompts.

### 19.2. Какие состояния очищаются

Очищение `authFlow` происходит:

- после успешного завершения регистрации;
- после успешного завершения восстановления пароля.

Обычный вход `signin` `authFlow` не использует.

### 19.3. Какие состояния не очищаются автоматически

При закрытии шторки кода или возврате на телефонный шаг:

- введенный номер сохраняется;
- его не нужно вводить заново.

Post-login permission prompts после показа не возвращаются в исходное состояние автоматически.

## 20. Что важно не сломать при дальнейшей разработке

- `step=code` нельзя трактовать как отдельную full-screen страницу, пока текущая реализация использует bottom sheet.
- Demo-code `123456` сейчас зашит в коде. При переходе на backend его нужно будет заменить и в validate, и в resend-flow.
- Таймер resend завязан на client-side `setInterval`. При серверной интеграции важно определить, остается ли это только UI-ограничением или становится продуктовым.
- `notice=password-reset` используется сразу для двух сценариев: завершение регистрации и завершение восстановления пароля.
- Обычный логин сразу проставляет `setupCompleted: true`, поэтому setup-flow и auth-flow сейчас логически разделены.
- Post-login prompts и setup permissions — разные сущности. Нельзя сводить их к одному булевому полю без пересмотра логики.

## 22. Доменные сущности и правила данных

Этот раздел описывает, какие сущности живут в приложении, откуда они берутся, как собираются итоговые модели для экранов и какие правила действуют при изменении данных.

## 23. Общая модель данных

### 23.1. Три типа источников

Почти все продуктовые данные собираются из трех слоев:

1. статический seed в `src/app.js`;
2. пользовательские записи в `localStorage`;
3. derived-модели, которые объединяют seed и пользовательские изменения.

На практике это выглядит так:

- статические клиенты лежат в `clients`, `clientDetails`, `taskCards`, `taskDetails`, `callHistoryEntries`, `chatThreads`;
- пользовательские сущности и правки лежат в `created*`, `*Overrides`, `deleted*`;
- экран почти никогда не читает seed напрямую, а использует `getClients()`, `getTaskCards()`, `getTaskDetail()`, `getClientDetail()`, `getChatConversationModel()` и похожие getter-функции.

### 23.2. Что считается seed-данными

К seed-данным относятся:

- каталог базовых клиентов `clients`;
- подробности клиента `clientDetails`;
- карточки задач `taskCards` и их порядок `taskCardOrder`;
- детальные модели задач `taskDetails`;
- справочники сотрудников `employeeDirectoryProfiles`;
- справочники телефонной книги `phoneBookDirectoryProfiles`;
- история звонков `callHistoryEntries`;
- список чатов `chatThreads`;
- разговоры по чатам `chatConversationById`;
- словари статусов, типов и визуальных вариантов.

### 23.3. Что считается пользовательскими данными

К пользовательскому слою относятся:

- созданные клиенты;
- созданные задачи;
- переопределения для seed-клиентов и seed-задач;
- мягкие удаления seed-клиентов и seed-задач;
- сохраненные касания;
- pending-touch для анализа;
- список уже проанализированных touch ids.

## 24. Сущность «Клиент»

### 24.1. Базовая карточка клиента

Seed-клиент из массива `clients` содержит минимум:

- `id`
- `name`
- `company`
- `initials`
- `photo`

Это только базовый каталог. Полная карточка клиента собирается отдельно.

### 24.2. Расширенная клиентская модель

При импорте или пользовательском создании клиент фактически имеет набор полей:

- `id`
- `name`
- `company`
- `initials`
- `photo`
- `description`
- `email`
- `phone`
- `price`
- `position`
- `status`
- `badgeLabel`
- `createdAt`

Не все поля обязательны для отображения, но именно такой payload используется при сохранении формы клиента.

### 24.3. Источник истины для списка клиентов

Текущий каталог клиентов строится через `getClients()`.

Он:

- берет только `getCreatedClients()`;
- исключает ids из `deletedClients`;
- применяет `clientOverrides` по совпадающему `id`;
- нормализует статус через `normalizeClientStatus()`;
- пересчитывает `initials` из актуального имени.

Важно: после внедрения импорта из CRM базовые seed-клиенты попадают в рабочий каталог через `saveCreatedClients()`. То есть в ежедневной логике `getClients()` опирается именно на persisted-слой.

### 24.4. Создание клиента

При создании клиента обязательны:

- `lastName`
- `phone`

Кнопка submit активируется только когда оба поля заполнены.

При submit:

- `name` собирается либо из отдельного `name`, либо из `firstName + lastName`;
- `status` нормализуется;
- `price` форматируется в `₽`, если значение есть;
- `createdAt` ставится как `new Date().toISOString()`;
- `id` генерируется как `client-${Date.now()}`;
- `photo` для нового клиента всегда пустой строкой.

### 24.5. Редактирование клиента

При редактировании:

- если клиент уже есть в `createdClients`, запись обновляется там;
- если это seed-клиент, изменения пишутся в `clientOverrides`;
- `photo` стараются сохранить из текущего клиента;
- `createdAt` для существующего клиента сохраняется.

### 24.6. Удаление клиента

Удаление клиента каскадное.

Функция `deleteClient(clientId)` делает следующее:

- удаляет клиента из `createdClients`;
- удаляет связанные пользовательские задачи из `createdTasks`;
- удаляет override клиента;
- удаляет task overrides для seed-задач, связанных с этим клиентом;
- добавляет связанные seed-task ids в `deletedTasks`;
- очищает pending touch;
- очищает analyzed touches;
- удаляет сохраненные touches клиента;
- если клиент был seed-клиентом, добавляет его id в `deletedClients`.

Это означает, что удаление клиента скрывает весь связанный рабочий контекст.

### 24.7. Полная детальная модель клиента

`getClientDetail(clientId)` собирает клиентскую карточку для detail screen.

Она включает:

- `profile`
  - `id`
  - `initials`
  - `name`
  - `company`
  - `photo`
- `summary`
  - `description`
  - `price`
  - `badges`
- `contacts`
  - `Телефон`
  - `Почта`
- `activities`

Особенности:

- если для клиента есть seed-detail в `clientDetails`, он используется как база;
- если detail нет, строится fallback-модель;
- `description`, `phone`, `email`, `price` берутся из актуального клиента и имеют приоритет над seed;
- `activities` = `savedTouches + sourceActivities`.

То есть пользовательские касания всегда в начале списка и расширяют, а не заменяют исходную активность.

## 25. Статусы клиента

### 25.1. Допустимые статусы

Словарь `clientStatusOptions` содержит:

- `hot`
- `warm`
- `cold`
- `non-target`
- `closed`

Отображаемые подписи:

- `Горячий`
- `Теплый`
- `Холодный`
- `Нецелевой`
- `Закрытый`

### 25.2. Нормализация статуса

`normalizeClientStatus()` приводит старые и неполные значения к валидному статусу.

Поведение:

- пустое значение -> `cold`
- `active` -> `cold`
- `ordinary` -> `cold`
- `new` -> `cold`
- `lead` -> `non-target`

### 25.3. Производные правила по статусу

В логике приложения используются три важных derived-проверки:

- `isNonTargetClient`
- `isClosedClient`
- `isHiddenClient`

`isHiddenClient` возвращает `true` для:

- `non-target`
- `closed`

Это влияет на каталоги, фильтры, задачи и дайджест.

### 25.4. Дополнительный badge «Новый»

Клиент считается новым через `isClientNew(client)`, если:

- у него есть `createdAt`;
- с момента создания прошло меньше 7 дней.

Этот badge существует параллельно со статусом.

Итоговый набор badges клиента формируется через `getClientStatusBadges()`:

- основной status badge;
- optional badge `Новый`.

## 26. Директории контактов

### 26.1. Три режима каталога

Экран контактов может работать в трех режимах:

- `clients`
- `employees`
- `phonebook`

### 26.2. Как устроены `employees` и `phonebook`

Это не отдельные сущности с собственным жизненным циклом.

Обе директории строятся как проекция поверх `baseClients`:

- сохраняется тот же `id`;
- заменяются `name`, `company`, `initials` из соответствующего справочника;
- остальные поля клиента продолжают жить из основной клиентской модели.

Следствие:

- сотрудники и телефонная книга наследуют часть поведения клиентов;
- у них нет независимого CRUD;
- сортировки и группировки используют уже преобразованный `name`.

### 26.3. Ограничение по RMO

Если `rmoFeaturesEnabled = false`, директория `employees` принудительно отключается:

- `contactsTab=employees` возвращается в `clients`.

## 27. Сущность «Задача»

### 27.1. Seed-задачи

Seed-список задач состоит из:

- `taskCards` — краткие карточки для списков;
- `taskDetails` — полные модели detail screen;
- `taskCardOrder` — порядок seed-задач.

`taskCards` содержат:

- `id`
- `clientId`
- `size`
- `badge` или `badges`
- `title`
- `subtitle`
- `description`
- `price`
- `status`

`taskDetails` содержат:

- `clientId`
- `summary`
  - `title`
  - `badges`
  - `paragraphs`
- `client`
- `relatedTask`
- `activities`

### 27.2. Пользовательская задача

При создании новой задачи используются поля:

- `id`
- `title`
- `client`
- `type`
- `time`
- `description`

`id` создается как `created-${Date.now()}`.

### 27.3. Обязательные поля новой задачи

Для новой задачи обязательны:

- `title`
- `client`
- `type`

`time` опционален, fallback:

- `Сегодня, 14:00`

`description` опционально.

### 27.4. Редактирование задачи

Редактирование работает через `saveTaskEditModel()`.

Если задача пользовательская:

- обновляется запись в `createdTasks`.

Если задача seed:

- изменения пишутся в `taskOverrides`, но только если override реально отличается от base-модели;
- если различий больше нет, override удаляется.

### 27.5. Что считается edit-моделью задачи

`getTaskEditModel(taskId)` возвращает единый edit contract:

- `id`
- `title`
- `client`
- `type`
- `time`
- `description`
- `completedFromTime`
- `isCreated`

Этот контракт используется и для seed-задач, и для пользовательских.

### 27.6. Детальная модель задачи

`getTaskDetail(taskId)` выбирает:

- `getCreatedTaskDetail(createdTask)` для пользовательских задач;
- `getStaticTaskDetail(taskId)` для seed-задач.

Для пользовательской задачи detail собирается на лету из:

- task fields;
- client option;
- task type label;
- fallback-описаний активности.

### 27.7. Типы задач

Словарь `taskTypeOptions`:

- `call` -> `Связаться с клиентом`
- `proposal` -> `Отправить документы`
- `viewing` -> `Личная встреча`
- `followup` -> `Другое`

Тип влияет на:

- badge задачи;
- иконку в дайджесте;
- предложенный визуальный тон;
- подписи в detail и списках.

### 27.8. Определение типа по тексту

Если тип нужно восстановить по label, используется `getTaskTypeByLabel()`.

В ней есть эвристики по ключевым словам:

- документы / предложение / подборка -> `proposal`
- встреча / просмотр -> `viewing`
- звонок / связаться / контакт -> `call`
- другое / повтор -> `followup`

Это важно для совместимости между seed-моделями, overrides и визуальными компонентами.

### 27.9. Завершение и переоткрытие задачи

Завершение:

- для created task заменяет `time` на `Завершено`;
- прежнее время переносит в `completedFromTime`.

Для seed-задачи:

- тот же эффект записывается в `taskOverrides`.

Переоткрытие:

- берет `completedFromTime`, если он есть;
- если значение снова похоже на completed-state, подставляет `Сегодня, 14:00`.

### 27.10. Удаление задачи

При удалении:

- задача удаляется из `createdTasks`;
- override по id удаляется;
- если это seed-задача, ее id добавляется в `deletedTasks`.

Это мягкое удаление для seed и полное удаление для created task.

## 28. Периоды и статусы задач

### 28.1. Как определяется период задачи

`getTaskPeriod(card)` возвращает одно из значений:

- `today`
- `future`
- `completed`
- `non-target`

Логика:

- если клиент задачи `non-target` -> `non-target`;
- если status label начинается с `Завершено` -> `completed`;
- если label пустой, начинается с `Просрочено`, `Сегодня` или `в ` -> `today`;
- если дата распарсилась и она позже today -> `future`;
- если дата распарсилась и она сегодня или раньше -> `today`.

### 28.2. Completion-state

Признак completed определяется просто:

- `isTaskCompletedTime(value)` проверяет, начинается ли строка с `Завершено`.

То есть completion — это строковое состояние времени, а не отдельное булево поле.

### 28.3. Временные представления

Для задач существуют три разных формата времени:

- raw edit value;
- list/detail display value;
- normalized edit fallback после completed/reopen.

Ключевые функции:

- `normalizeTaskTimeForEdit()`
- `formatDisplayDateText()`
- `formatClientTaskRowDetail()`

## 29. Связь клиента и задачи

### 29.1. Откуда задача берет клиента

Каждая задача ссылается на клиента через:

- `clientId` в карточке;
- `client` в edit-модели и created task.

### 29.2. Производные данные клиента в задаче

При сборке task card и task detail дополнительно подтягиваются:

- актуальное имя клиента;
- компания;
- price;
- badges клиента.

Это значит, что изменение клиента автоматически меняет:

- subtitle задач;
- цены в карточках;
- status badges рядом с задачами.

### 29.3. Активные задачи клиента

`getClientActiveTaskRows(clientId)` использует:

- все карточки задач;
- фильтр `getTaskPeriod(task) !== "completed"`.

Фильтр `Без задач` в клиентах полностью зависит от этого расчета.

## 30. Сущность «Касание»

### 30.1. Где живут касания

Касания делятся на два слоя:

- seed-активность из `clientDetails[*].activities`;
- пользовательские касания из `clientTouches`.

Дополнительно есть:

- `pendingClientTouches` — временное новое касание перед анализом;
- `analyzedClientTouches` — список уже проанализированных touch ids.

### 30.2. Формат сохраненного касания

`addClientTouch()` сохраняет объект вида:

- `id`
- `icon`
- `tone`
- `title`
- `subtitle`
- `time`

Касание всегда добавляется в начало массива клиента.

### 30.3. Специализированные типы касаний

Есть helper-функции:

- `addClientCallTouch()`
- `addClientChatTouch()`
- `addClientMeetingTouch()`

Они проставляют дефолтные:

- icon;
- tone;
- title;
- формат времени.

### 30.4. Формат времени касаний

Для звонка:

- `14 марта 2026 с 12:20 по 14:30`

Для чата:

- `С 14 по 15 марта 2026`

Для встречи:

- используется общий call-like time format, если не задано иное.

### 30.5. Pending touch

`setPendingClientTouch(clientId, touch)` сохраняет незавершенное касание для анализа.

По умолчанию туда подставляется:

- `type: "call"`
- `title: "Звонок"`
- текущее время в формате call touch

Pending touch:

- участвует в сценариях call results;
- может показывать inline notice `Новые касания`;
- не равен сохраненному activity item, пока не будет обработан.

### 30.6. Анализированные касания

Список `analyzedClientTouches[clientId]` хранит только массив ids.

Он нужен для того, чтобы:

- понимать, какие касания уже отправлялись на AI-анализ;
- управлять notice и связанными экранами;
- чистить stale ids при удалении касаний.

### 30.7. Удаление касания

Удаление касания:

- убирает запись из `clientTouches[clientId]`;
- удаляет его id из analyzed ids.

Seed-активности из `clientDetails` этим не затрагиваются.

## 33. Результаты анализа звонка

### 33.1. Это не отдельная persist-сущность

Экран call results строится динамически, без отдельного storage-объекта.

Он зависит от:

- `clientId`
- `taskId`
- pending touch;
- latest saved touch;
- текущих задач клиента;
- текущего locale.

### 33.2. Что в него входит

Call results собирают как минимум два блока:

- обновления данных клиента;
- обновления задач.

### 33.3. Data updates

`getCallResultDataUpdates()` сейчас генерирует только 2 поля:

- `Бюджет`
- `Статус`

Это соответствует текущей продуктовой логике, где все остальные поля на экране были сознательно убраны.

### 33.4. Task updates

`getCallResultTaskUpdates()` может вернуть:

- update для уже существующей открытой задачи с возможностью завершить/переоткрыть;
- suggestion новой задачи.

То есть call results не просто показывают summary, а формируют следующую операционную работу.

### 34.1. Источник для дайджеста

Утренний дайджест берет все задачи из:

- seed task cards;
- created tasks;
- с учетом deleted ids;
- с учетом overrides.

### 34.2. Что агрегируется

`getMorningDigestModel()` считает:

- `totalCount`
- `meetingsCount`
- `callsCount`
- `proposalCount`
- `clientsCount`
- `hotAgenda`
- `otherAgenda`
- `noTaskClients`
- `tomorrowAgenda`

### 34.3. Что считается клиентом без задач

В дайджесте и каталоге контактов клиент без задач — это клиент, у которого:

## 35. Поиск как cross-entity слой

Поиск в приложении не имеет собственной сущности.

Это объединяющий слой поверх:

- клиентов;
- задач;
- связанных текстовых полей.

Для поиска используется нормализация:

- lowercase;
- замена `ё` на `е`;
- чистка html/entities и лишних символов;
- токенизация по словам.

Это значит, что качество поиска сильно зависит от того, какие текстовые поля попадают в индексацию на этапе рендера результатов.

## 36. Что важно не сломать в слое данных

- `getClients()` и `getTaskCards()` — это реальные source-of-truth для экранов. Если читать seed-массивы напрямую, экран начнет расходиться с persisted state.
- Клиентские директории `employees` и `phonebook` завязаны на ids обычных клиентов. Если изменить id-схему, обе директории развалятся.
- Completion задачи завязан на строковое значение `time`, а не на отдельный bool.
- Client detail screen всегда объединяет `savedTouches` и seed-activity. Если заменить это поведение, можно потерять историю.
- Удаление клиента каскадно влияет на задачи и касания. Это важно учитывать перед любыми миграциями хранения.
- `call-results` сейчас derived-only. Если позже появится серверное сохранение результатов, нужно будет определить, какие поля становятся canonical.

## 39. Экран `#/clients`

### 39.1. Назначение экрана

`#/clients` — это единая точка входа в контактный контур приложения.

Экран может показывать:

- обычных клиентов;
- сотрудников;
- телефонную книгу.

Фактически route один и тот же, а содержимое переключается через query-параметры.

### 39.2. Режимы экрана

Режим директории определяется через `getContactsDirectoryFromUrl()`.

Поддерживаются:

- `clients`
- `employees`
- `phonebook`

Источник переключения:

- query `contactsTab`

Поведение:

- если `contactsTab` пустой -> `clients`;
- если `contactsTab=employees` и RMO выключен -> принудительно `clients`;
- если `contactsTab=phonebook` -> `phonebook`.

### 39.3. Заголовок экрана

Во всех трех режимах title сейчас один:

- `Контакты`

Разница идет по доступным действиям и сегментам.

### 39.4. Правый action в header

- в `employees` скрыта;
- в `phonebook` скрыта.

Label для `clients`:

- `Добавить клиента`

Следствие:

- создать новую запись можно только в клиентском каталоге;
- сотрудники и телефонная книга работают как read-only представления.

## 40. Каталог клиентов: состав, фильтры и сортировки

### 40.1. База списка

Для каталога берется:

- `allClients = getDirectoryClients(directory)`

То есть:

- в `clients` берется обычный клиентский список;
- в `employees` и `phonebook` — его проекции.

### 40.2. Верхние сегменты каталога

Верхний сегмент собирается динамически.

Базовый набор:

- `Клиенты`

Дополнительно, только если есть данные:

- `Горячие`
- `Без задач`
- `Нецелевые`
- `Закрытые`

Отдельно, если `rmoFeaturesEnabled = true`:

- `Сотрудники`

Badge count берется из `getClientFilterCounts(allClients)`.

### 40.3. Как считаются счетчики

`getClientFilterCounts()` возвращает:

- `all`
- `hot`
- `no-tasks`
- `non-target`
- `closed`

Логика:

- `all` считает только не hidden-клиентов;
- `hot` считается только внутри общих активных клиентов;
- `no-tasks` считается только внутри общих активных клиентов;
- `non-target` и `closed` считаются отдельными корзинами.

### 40.4. Правило hidden-клиентов

В базовый общий список не входят:

- `non-target`
- `closed`

Поэтому вкладка `Клиенты` означает:

- все клиенты, кроме нецелевых и закрытых.

Это важное продуктовое правило для всей навигации.

### 40.5. Эффективный фильтр

Даже если query-параметр указывает на фильтр, которого больше нет в данных, приложение не оставляет экран пустым из-за устаревшего состояния.

Работает fallback:

- если выбран `hot`, но горячих нет -> `all`;
- если выбран `no-tasks`, но таких клиентов нет -> `all`;
- если выбран `non-target`, но таких нет -> `all`;
- если выбран `closed`, но таких нет -> `all`.

### 40.6. Реальная фильтрация списка

`getFilteredClients()` работает так:

- `non-target` -> только non-target;
- `closed` -> только closed;
- `hot` -> только hot из общего активного списка;
- `no-tasks` -> только активные клиенты без активных задач;
- `all` -> активные клиенты без hidden-статусов.

### 40.7. Сортировки каталога

Поддерживаются 4 сортировки:

- `hot`
- `with-tasks`
- `alphabet`
- `new`

Поведение:

- `hot` — горячие выше остальных;
- `with-tasks` — клиенты с активными задачами выше;
- `alphabet` — по фамилии, затем по имени;
- `new` — новые созданные записи выше seed-клиентов.

### 40.8. Sort menu

Sort menu открывается по левой кнопке header.

Пункты:

- `Сначала горячие`
- `Сначала с задачами`
- `По алфавиту`
- `Сначала новые`

Значение хранится в query-параметре:

- `clientsSort`

Если выбрана дефолтная сортировка `hot`, параметр удаляется из URL.

## 43. Добавление клиента и импорт из CRM

### 43.1. Меню добавления

И в обычном каталоге, и в пустом состоянии используется один и тот же сценарий:

- клик по add trigger открывает glass menu;
- клик снаружи закрывает menu.

### 43.2. Вариант `Добавить вручную`

При выборе:

- пользователь переводится на `#/new-client`

### 43.3. Вариант `Добавить из CRM`

При выборе:

- открывается progress modal `Импорт из CRM`;
- запускается таймер на `2000ms`;
- после таймера вызывается `importClientsFromCrm()`;
- `clientsState` удаляется из URL;
- route переводится на `#/clients`;
- выполняется `render()`.

### 43.4. Что делает `importClientsFromCrm()`

Импорт:

- берет seed-клиентов;
- пропускает тех, кто уже есть в `createdClients`;
- преобразует их в рабочий client payload через `getStaticClientForImport()`;
- добавляет их в `createdClients`;
- убирает их ids из `deletedClients`, если они раньше были скрыты.

То есть импорт можно воспринимать как начальную загрузку основной клиентской базы в persisted-слой.

Меню `Еще` содержит:

На карточке клиента всегда рендерятся 4 действия:

- `Позвонить`

- `Задача`

Если клиент не private и для него есть необработанные касания, показывается notice:

### 46.7. Блок задач клиента

Секция `ЗАДАЧИ` строится через `renderClientTasks(tasks, addTaskHref, archiveHref)`.

Поведение:

- если задач нет -> строка `Задач нет` + CTA `Добавить задачу`;
- если задачи есть -> показываются первые 2;
- footer `Архив задач` показывается только если у клиента есть хотя бы одна выполненная задача;

Важно:

- в карточке клиента нет полного списка всех задач клиента;
- она показывает компактный срез.

### 46.9. Касания клиента

Источник:

- `normalizeTouchActivities(activities, clientId)`

Каждый touch получает:

- вычисленный type;
- icon/tone;
- `id`;
- href в `#/touch?...`.

## 51. Что важно не сломать в разделе Контакты

- Вкладка `Клиенты` по смыслу исключает `non-target` и `closed`. Это важная продуктовая семантика.
- `employees` и `phonebook` нельзя переводить в самостоятельный CRUD без пересмотра их data-model.
- В каталоге `delete` из swipe сейчас происходит без confirm modal. Если менять это поведение, нужно учитывать скорость массовой чистки.
- Карточка клиента собирает активности из двух источников: saved touches и source activities.
- Empty state контактов зависит не только от отсутствия данных, но и от `clientsState=empty`.
- Импорт из CRM сейчас asynchronous only by timer, но уже влияет на persisted state и снимает deleted-маску с импортируемых клиентов.

## 54. Экран `#/tasks`

### 54.1. Назначение

Экран задач — это главный операционный список дня.

У экрана два режима:

- `Списком` — основной режим по умолчанию;
- `По датам` — режим календарного просмотра.

Отдельно существует специальный режим архива задач клиента через query `clientArchive`.

### 54.2. Источник данных

Для списка используется:

- `allCards = getTaskCards()`

Дальше экран одновременно готовит:

- периодные корзины через `getTaskPeriod(card)` и `isClosedTaskCard(card)`;
- дату каждой задачи для режима `По датам`.

Для режима `По датам` действует правило:

- если задача активная, используется ее плановая дата;
- если задача завершена, используется дата завершения `completedAt`.

### 54.3. Корзины задач

Экран строит отдельные массивы:

- `todayCards`
- `futureCards`
- `completedCards`
- `nonTargetCards`
- `closedCards`

Эти массивы используются для счетчиков и для режима `Списком`.

Для режима `По датам` дополнительно собираются:

- `calendarDays` — набор дней для горизонтальной ленты;
- `dateViewCards` — задачи выбранного дня.

### 54.4. Режим `Списком`

Это дефолтный режим, если query `tasksView` отсутствует.

В этом режиме верхний сегмент всегда начинается с:

- `Сегодня`
- `Будущие`

Дополнительно, только если есть данные:

- `Готовые`
- `Нецелевые`
- `Закрытые`

Badge каждого сегмента показывает количество элементов в соответствующей корзине.

В английской локали эти же пункты переводятся через словарь интерфейса.

### 54.5. Fallback по невалидному выбранному периоду в режиме `Списком`

Если в URL выбран период, у которого больше нет данных, экран сам возвращается к `today`.

Это работает для:

- `non-target`
- `closed`
- `completed`

Таким образом устаревший query не оставляет пользователя на пустом фильтре.

### 54.6. Режим `По датам`

Режим включается через query:

- `tasksView=date`

Дополнительно экран хранит выбранный день:

- `taskDate=YYYY-MM-DD`

Вместо периодного сегмента экран показывает горизонтальную ленту дат:

- лента скроллится в обе стороны;
- лента собрана по неделям;
- на одном экране показывается 7 плашек, по одной на день недели;
- горизонтальный скролл перелистывает сразу целую неделю;
- выбранный день подсвечивается brand-цветом;
- текущий день в невыбранном состоянии получает subtle brand-подложку;
- после открытия выбранный день прокручивается в видимую область;
- подпись дня локализуется;
- верхняя строка плашки показывает только число месяца.

Для каждой карточки день вычисляется так:

- активная задача попадает в день своего планового события;
- завершенная задача попадает в день, когда она была завершена.

Порядок задач внутри выбранного дня:

- сначала активные задачи;
- затем завершенные;
- внутри группы сохраняется сортировка по времени и исходному порядку.

Если на выбранный день задач нет, экран показывает отдельное пустое состояние:

- title `На этот день задач нет`;
- description с предложением выбрать другой день или создать новую задачу;
- показывается стандартная иллюстрация empty-state задач;
- CTA на создание задачи.

При переключении между режимами:

- выбранный `taskDate` не сбрасывается;
- если пользователь уходит в `Списком` и возвращается в `По датам`, открывается тот же день.

### 54.7. Header списка задач

В обычном экране задач header всегда содержит:

- centered title `Задачи` в режиме `Списком`;
- centered title `Задачи на <месяц>` в режиме `По датам`;
- слева кнопку текущего режима;
- справа кнопку `Добавить`;

Поведение левой кнопки режима:

- в режиме `Списком` label `Списком`;
- в режиме `По датам` label `По датам`;
- в режиме `По датам` используется иконка `calendar-outline`;
- по нажатию экран переключается на другой режим, сохраняя контекст страницы.

### 54.8. Режим архива задач клиента

Экран `#/tasks` может открываться в специальном режиме архива клиента, если в URL есть query `clientArchive`.

Условия:

- `clientArchive` должен совпасть с существующим `clientId`;
- список показывается только для completed tasks этого клиента.

В этом режиме:

- верхний сегмент-переключатель периодов скрыт;
- лента дат скрыта;
- header получает левую кнопку `Назад`;
- `Назад` возвращает в карточку этого клиента `#/clients/<clientId>`;
- справа показывается `plus`, который ведет в создание новой задачи именно для этого клиента;
- на экране остаются только выполненные задачи выбранного клиента.

Если completed tasks у клиента нет:

- раздел `Архив задач` в карточке клиента вообще не рендерится;
- открыть этот режим можно только прямым URL.

## 55. Пустые состояния задач

### 55.1. Общий empty screen

Существует отдельный технический экран `renderTasksEmptyApp()`, но основной route `#/tasks` чаще использует встроенные empty-variant’ы внутри списка периода.

### 55.2. Пустое состояние для `today`

`today` имеет 2 варианта:

- `none`
- `done`

Variant определяется так:

- если `tasksState=done` -> `done`;
- если `tasksState=empty` или `tasksState=none` -> `none`;
- иначе если `completedCards.length > 0` -> `done`;
- иначе -> `none`.

### 55.3. Today empty variant `none`

Состав:

- иллюстрация `tasksEmpty`;
- title `Сегодня задач нет`;
- description про добавление задачи;
- CTA `Добавить задачу`.

### 55.4. Today empty variant `done`

Состав:

- иллюстрация `tasksDone`;
- title `Отличная работа!`;
- description с количеством закрытых задач;
- CTA `Создать новую задачу`.

Это специальный reward-state после закрытия дневных задач.

### 55.5. Пустое состояние для `future`

Когда выбран `future` и задач нет:

- title `Будущих задач пока нет`;
- description про планирование следующего контакта;
- CTA `Запланировать задачу`.

### 55.6. Когда показывается реальный список

Список карточек рендерится, только если:

- нет today-empty state;
- нет future-empty state.

Во всех остальных случаях центр страницы занят empty-state.

## 56. Header и действия списка задач

### 56.1. Header

В обычном режиме `#/tasks` header не использует сортировку.

Вместо нее доступны:

- `Добавить` -> `#/new-task`;
- `По датам` или `Списком` -> переключает представление без ухода со страницы.

### 56.2. Список карточек

Когда список не пустой, рендерится:

- `.cg-tasks-list`

Каждая карточка оборачивается в `renderTaskSwipeCell(card, { href })`.

То есть каждая задача одновременно:

- кликабельна;
- поддерживает swipe actions.

## 57. Карточка задачи в списке

### 57.1. Состав task card

Карточка показывает:

- badge или badges;
- title;
- subtitle;
- description;
- price;
- status badge.

### 57.2. Footer карточки

Если статус — одиночный badge:

- price и status стоят в одной строке.

Если статус выглядит как range/длинный лейбл:

- footer перестраивается в stacked-вариант.

### 57.3. Badges карточки

Карточка может иметь:

- один основной badge `card.badge`;
- массив badges `card.badges`.

В задачах клиента badges могут включать клиентские статусы:

- `Горячий`
- `Нецелевой`
- `Закрытый`
- `Новый`

## 58. Swipe-действия в списке задач

### 58.1. Набор действий

У карточки задачи по свайпу доступны:

- `Завершить` или `Открыть`
- `Изменить`
- `Удалить`

Первая кнопка зависит от completion-state задачи.

### 58.2. Поведение `Завершить / Открыть`

Если задача не завершена:

- вызывается `completeTask(taskId)`;
- затем `render()`.

Если завершена:

- вызывается `reopenTask(taskId)`;
- затем `render()`.

### 58.3. Поведение `Изменить`

Открывает:

- `#/edit-task/<taskId>?back=<currentHash>`

### 58.4. Поведение `Удалить`

Сразу вызывает:

- `deleteTask(taskId)`
- `render()`

На swipe-уровне отдельного confirm нет.

### 58.5. Общая логика свайпа

Как и в клиентах:

- одновременно может быть открыта одна строка;
- click/tap по открытой строке закрывает ее;
- click вне строки закрывает все;
- vertical gesture не должен срабатывать как swipe.

## 59. Long-press и context menu задач

### 59.1. Где работает

Long-press доступен на `.cg-task-card--link[data-task-card-id]`.

Триггеры:

- press-and-hold ~420ms;
- `contextmenu` как desktop fallback.

### 59.2. Меню long-press

Меню содержит:

- `Перенести задачу`
- `Завершить задачу` или `Открыть`
- `Удалить задачу`

### 59.3. `Перенести задачу`

Открывает date-time picker внутри отдельного overlay root.

После сохранения:

- новое время записывается в `saveTaskEditModel(taskId, { time: nextTime })`;
- экран перерисовывается.

### 59.4. `Завершить / Открыть`

Открывает confirm modal.

Тексты modal зависят от действия:

- `Завершить задачу?`
- `Открыть задачу заново?`

Кнопки modal:

- слева всегда `Отмена`;
- справа брендовая кнопка:
  - `Завершить`
  - `Открыть`

После подтверждения вызывается:

- `completeTask(taskId)` или
- `reopenTask(taskId)`

### 59.5. `Удалить задачу`

Открывает confirm modal:

- `Удалить задачу?`

После подтверждения:

- `deleteTask(taskId)`
- `render()`

## 60. Карточка задачи `#/task/:id`

### 60.1. Общая структура

Task detail screen содержит:

1. header с меню `Еще`;
2. summary card задачи;
3. action tiles;
4. call/chat progress modal binding;
5. delete / complete alert modals;
6. клиентский summary block;
7. список касаний клиента;
8. optional переход в call results.

### 60.2. Header

Header:

- back на `#/tasks`;
- title `Задача`;
- меню `Еще`.

Меню содержит:

- `Редактировать`
- `Удалить`

### 60.3. Summary card

Summary block рендерится через `renderTaskSummaryCard(detail.summary)`.

Он показывает:

- заголовок задачи;
- badges summary;
- paragraphs с контекстом.

Есть дополнительное правило:

- badge `Другое` из `followup` скрывается в summary, если он совпадает с followup type label.

### 60.4. Action tiles

На detail-экране задачи есть 3 действия:

- `Позвонить`
- `Написать`
- `Завершить` или `Открыть`

`Позвонить` и `Написать`:

- выключаются, если у клиента нет телефона.

`Завершить`:

- если задача активна, показывает complete-flow;
- если задача завершена, превращается в `Открыть`.

### 60.5. Меню `Еще`

Из меню:

- `Редактировать` ведет на `#/edit-task/<id>?back=<currentHash>`;
- `Удалить` открывает delete modal.

### 60.6. Complete modal

При подтверждении:

- если задача уже completed -> `reopenTask(taskId)` и переход в соответствующий список периода;
- если активная -> `completeTask(taskId)` и перевод в `completed` period.

Это делается через:

- `setTaskListRoute(getTaskListPeriodForTask(taskId))` для reopen;
- `setTaskListRoute("completed")` для complete.

### 60.7. Delete modal

При подтверждении:

- `deleteTask(taskId)`
- переход в список `today`

### 60.8. Связанные клиент и касания

Task detail использует клиентский контекст:

- `clientId` берется из detail/task model;
- действия и коммуникации завязаны на этого клиента;
- список touches клиента используется как рабочая история рядом с задачей.

## 61. Создание задачи `#/new-task`

### 61.1. Базовый сценарий

Экран создания задачи строится через `renderCreateTaskForm()`.

Route может приходить:

- без выбранного клиента;
- с `selectedClient` из path;
- с `back` в query;
- с preset из `call results`.

### 61.2. Предзаполнение клиента

Если route содержит client id и он валиден:

- поле клиента предзаполняется этим значением.

Если нет:

- поле пустое.

### 61.3. Обязательные поля

Для новой задачи обязательны:

- `Название`
- `Клиент`
- `Тип задачи`

Без них submit недоступен.

### 61.4. Необязательные поля

Опциональны:

- `Время`
- `Описание`

Если время пустое, при сохранении используется:

- `Сегодня, 14:00`

### 61.5. Итог сохранения

На submit создается объект:

- `id: created-${Date.now()}`
- `title`
- `client`
- `type`
- `time`
- `description`

Он добавляется в `createdTasks`.

После этого:

- пользователь уходит на `back` из query;
- если `back` нет, открывается `#/task/<newId>`.

### 61.6. Preset из call results

Если query содержит:

- `preset=call-result-new`

экран предзаполняется значениями:

- `taskTitle`
- `taskType`
- `taskTime`
- `taskDescription`

Если каких-то значений нет, используются fallback-тексты для follow-up after call.

## 62. Редактирование задачи `#/edit-task/:id`

### 62.1. Источник модели

Edit screen строится из:

- `getTaskEditModel(taskId)`

То есть работает одинаково для created task и seed task.

### 62.2. Поля формы

Редактирование включает:

- `Название`
- `Клиент`
- `Тип задачи`
- `Дата/время`
- `Описание`

### 62.3. Обязательность

Для edit screen обязательным считается только:

- `title`

Клиент, тип и время могут fallback-иться к уже существующим значениям модели.

### 62.4. Сохранение

На submit вызывается:

- `saveTaskEditModel(taskId, patch)`

Затем переход:

- на `back` из query;
- если его нет, на `#/task/<taskId>`.

## 63. Call progress и chat progress внутри задач

### 63.1. Где подключаются

В task detail автоматически подключается `bindCallProgressModal()`.

Это означает, что действия `Позвонить` и `Написать` запускают промежуточный flow коммуникации.

### 63.2. Завершение звонка

Если tracking разрешен:

- создается новый call touch;
- открывается analysis sheet;
- затем пользователь может перейти в `call results`.

### 63.3. Завершение чата

Если tracking разрешен:

- создается новый chat touch;
- экран просто перерисовывается;
- отдельный analysis flow не стартует автоматически.

## 64. Экран `#/call-results`

### 64.1. Назначение

`call results` — промежуточный action screen после анализа звонка или клиентского анализа.

Он нужен для того, чтобы:

- обновить данные клиента;
- завершить текущую задачу;
- создать следующую задачу;
- перейти в редактирование клиента.

### 64.2. Входные параметры

Экран использует:

- `task`
- `client`
- `back`
- optional `analysis=client`

### 64.3. Заголовок экрана

Если `analysis=client`:

- title `Результаты анализа`

Иначе:

- `Результаты звонка`

### 64.4. Блок `ОБНОВЛЕНИЕ ЗАДАЧ`

Здесь показываются:

- visible task updates;
- CTA `Добавить задачу`.

Список task updates зависит от:

- текущей открытой задачи клиента;
- suggestion следующей задачи;
- массива `dismissedCallResultUpdates`.

### 64.5. Блок `ОБНОВЛЕНИЕ ДАННЫХ`

Сейчас содержит только:

- `Бюджет`
- `Статус`

И CTA:

- `Обновить другие данные`

Этот CTA ведет в:

- `#/edit-client/<clientId>?back=<currentCallResultsHref>`

### 64.6. Кнопка `Сохранить`

Кнопка внизу фиксирует завершение сценария и ведет на:

- `backHref`

`backHref` вычисляется из query и может вернуть:

- карточку клиента;
- карточку задачи.

### 64.7. Dismiss task updates

У task update есть dismiss-flow.

Если update скрыт:

- его `id` сохраняется в `dismissedCallResultUpdates`;
- после этого он больше не рендерится на экране.

### 64.8. Suggested new task flow

Если пользователь выбирает suggestion новой задачи, экран может перевести его на `new-task` с preset query-параметрами.

Это связывает `call results` с task creation flow без ручного переписывания текста.

## 65. Что важно не сломать в разделе Задачи

- `completed` состояние задачи сейчас полностью завязано на строку `time`.
- `today` empty state имеет 2 сценария и влияет на тон продукта: обычная пустота и reward-state.
- Swipe delete и long-press delete — разные UX-ветки: одно без confirm, другое с confirm.
- `edit-task` и `new-task` отличаются по обязательности полей.
- Task detail после complete/reopen/delete не просто перерисовывается, а переводит пользователя в правильный список периода.
- `call results` — это продолжение task workflow, а не отдельный изолированный экран аналитики.

## 67. Экранная логика: Касания, звонки и чаты

Этот блок описывает три связанных контура:

- клиентские касания;
- журнал звонков;
- inbox чатов.

Все три раздела работают с коммуникациями, но решают разные задачи:

- касания дают клиентский timeline;
- звонки дают историю телефонных событий;
- чаты дают рабочий inbox для переписок.

## 68. Экран `#/touches/:clientId`

### 68.1. Назначение

Экран показывает полный список касаний по выбранному клиенту.

Это расширенная версия блока `КАСАНИЯ`, который выводится:

- в карточке клиента;
- в карточке задачи.

### 68.2. Источник данных

Список строится из:

- `getClientTouchEntries(clientId)`
- `getFilteredTouches(...)`
- `renderTouchList(...)`

На экран попадают все касания клиента:

- звонки;
- чаты;
- встречи;
- сохраненные и созданные касания.

### 68.3. Параметры маршрута

Route:

- `#/touches/:clientId`

Query-параметры:

- `back`
- `touchFilter`

### 68.4. Поддерживаемые фильтры

`touchFilter` принимает значения:

- `all`
- `call`
- `chat`
- `meeting`

Если параметр отсутствует или невалиден, используется `all`.

### 68.5. Header и кнопка назад

Экран использует стандартный app header:

- title: `Все касания`
- left: back
- right: `Фильтр`

Назад вычисляется через `getTouchesBackTarget(clientId)`.

Поддерживаются два сценария:

- если `back=task:<taskId>`, переход на `#/task/<taskId>` и label `Назад к задаче`;
- в остальных случаях переход на `#/clients/<clientId>` и label `Назад к клиенту`.

### 68.6. Меню фильтра

По клику на `Фильтр` открывается glass menu:

- `Все касания`
- `Звонки`
- `Чаты`
- `Встречи`

Логика `bindTouchFilterMenu(clientId)`:

- при выборе `all` параметр `touchFilter` удаляется из URL;
- при выборе любого другого значения параметр пишется в `window.location.search`;
- route остается тем же;
- затем вызывается `render()`.

### 68.7. Содержимое списка

Строки списка рендерятся через общий рендер касаний.

Для каждой записи должны сохраняться:

- тип касания;
- время;
- заголовок;
- ссылка в detail.

### 68.8. Пустое состояние

Если после фильтрации касаний нет, пустое состояние отрабатывает внутри `renderTouchList(...)`. Отдельной route-логики для этого экрана нет.

## 69. Экран `#/touch`

### 69.1. Назначение

Экран показывает одно касание подробно:

- summary;
- transcript для звонка и чата;
- summary-only режим для встречи.

### 69.2. Входные параметры

Экран использует query-параметры:

- `client`
- `touch`
- `back`

Если `client` не передан, используется `omar`.

Если касание по `touchId` не найдено, собирается fallback-модель:

- title: `Звонок`
- time: `12 апреля 2026 в 09:15`
- icon: `call-outline`

### 69.3. Логика кнопки назад

Назад рассчитывается через `getTouchDetailBackTarget(clientId)`.

Поддерживаются сценарии:

- `back=task:<taskId>` -> `#/task/<taskId>`, `Назад к задаче`
- `back=client:<clientId>` -> `#/clients/<clientId>`, `Назад к клиенту`
- по умолчанию -> `#/touches/<clientId>?back=client:<clientId>`, `Назад к касаниям`

### 69.4. Заголовок и время

Header detail-экрана содержит:

- back button;
- title касания;
- строку времени под заголовком;
- optional menu справа.

Время формируется через `formatTouchDetailHeadlineTime(...)`.

Формат:

- русский: `12 июня в 09:15`
- английский: `June 12, 09:15`

### 69.5. Типы касаний

Экран поддерживает три рабочих типа:

- `call`
- `chat`
- `meeting`

Тип определяется через `getClientTouchType(touch)` и влияет на весь остальной UI.

### 69.6. Summary-блок

Summary-карточка рендерится всегда.

Текст summary берется по правилу:

1. `touch.subtitle`, если он непустой;
2. fallback из `getTouchSummaryText(type, touch)`.

Fallback summary:

- `chat` — краткое описание запроса клиента на сравнение объектов;
- `meeting` — `Описание встречи не добавлено.`;
- `call` — краткая сводка про бюджет, платежный план и подборку.

### 69.7. Transcript

Transcript-блок показывается только для:

- звонка;
- чата.

Для встречи transcript-секция не рендерится.

### 69.8. Источник transcript

Transcript собирается через `getTouchTranscriptMessages(type, touch)`.

Особенности:

- для `chat` используется зашитый demo-диалог с временем;
- для `call` используется зашитый demo-разговор менеджера и клиента;
- для `meeting` helper может вернуть одно summary-сообщение, но UI его не показывает.

В английской локали speaker и text переводятся через `translateText`.

### 69.9. Меню действий для встречи

Меню справа появляется только если одновременно выполнены условия:

- тип = `meeting`;
- у записи есть `touchId`.

Пункты меню:

- `Редактировать`
- `Удалить`

Если условий нет, справа рендерится скрытый placeholder для сохранения симметрии header.

## 70. Экран `#/calls`

### 70.1. Назначение

Экран показывает журнал звонков с группировкой по дням.

Он доступен только когда `rmoFeaturesEnabled = true`.

### 70.2. Источник данных

История строится на базе:

- `callHistoryEntries`
- `getCallHistoryRows()`
- `sortCallHistoryRows(...)`
- `groupCallsByDay(...)`

### 70.3. Sort mode

Текущее значение читается через `getCallsSortFromUrl()`.

Допустимые режимы:

- `new`
- `old`

Fallback:

### 70.4. Значение сортировок

`new`:

- сначала более новые дни;

`old`:

- сначала более старые дни;
- внутри дня более раннее время сверху.

`missed`:

- звонки, у которых `direction` начинается с `Пропущенный`, поднимаются вверх;

### 70.5. Header и верхние действия

Header экрана содержит:

- слева кнопку `Сортировка`;

- правая кнопка ведет на `#/dialer?back=%23/calls`.

### 70.6. Меню сортировки

Меню открывается из header и содержит:

- `Сначала новые`
- `Сначала старые`
- `Пропущенные сверху`

Логика `bindCallsSortMenu()`:

- при выборе `new` параметр `callsSort` удаляется;

- затем выполняется `render()`.

### 70.7. Группировка по дням

`groupCallsByDay(...)` собирает группы по календарной дате.

Заголовки групп формируются через `formatCallHistoryGroupLabel(...)`:

- `Сегодня`
- `Вчера`
- дата в формате `17 июня`

### 70.8. Строка звонка

Каждая запись показывает:

- icon/image слева в режиме `plain`;

Каждая строка ведет на:

- `#/call-results?source=history&callId=<id>`

Отдельной логики пустого состояния в текущем экране нет. Экран ожидает наличие seed-истории звонков.

## 71. Экран `#/chats`

### 71.1. Назначение

Экран показывает inbox чатов с единым scroll-сегментом фильтров.

### 71.2. Header

Шапка чатов собрана отдельно от стандартного `renderAppHeader`.

Состав:

Особенности:

Верхний сегмент чатов рендерится через `renderSegmentedControl(...)` с вариантом `pill`.

Свойства:

- scroll = false;
- badges = true;
- scope = `chats-scope`;

Пункты:

- `Групповые`
- `Чужие`

На экране `Заявки` этот `Pill` не показывается.

### 71.4. Нижний Topline-сегмент

Нижний сегмент появляется:

- в экране `Чаты`, если выбран верхний пункт `Мои чаты`;
- в экране `Заявки` всегда.

Свойства:

- variant = `topline`;
- scroll = true;
- badges = true;
- scope = `chats-status`.
- ширина пунктов определяется длиной текста и бейджа, без растягивания на равные колонки.
- в чатовом экране соседние пункты идут без дополнительного межколоночного gap.

Пункты:

- `Новые`
- `В работе`
- `Завершённые`

Если выбран любой другой верхний раздел, `Topline` не рендерится.

Если `Topline` отсутствует, между верхним `Pill` и списком чатов добавляется отдельный вертикальный отступ.

### 71.5. Query-параметры

Используются два параметра:

- `chatScope`
- `chatStatus`

`chatScope`:

- `mine` по умолчанию;
- допустимые значения `groups`, `external`, `requests`.

`chatStatus`:

- применяется к `Мои чаты` и к экрану `Заявки`;
- по умолчанию `new`;
- допустимые значения `active`, `completed`.

### 71.6. Обработчик переключения

`bindChatsApp()` навешивается на:

- `data-segment-scope="chats-scope"`
- `data-segment-scope="chats-status"`

Поведение верхнего `Pill`:

- `Мои чаты` удаляет `chatScope`;
- остальные пункты записывают свой `chatScope`;
- если выбран раздел не `Мои чаты`, `chatStatus` удаляется.

Поведение нижнего `Topline`:

- внутри `Мои чаты` работает в `chatScope = mine`;
- внутри экрана `Заявки` сохраняет `chatScope = requests`;
- `Новые` удаляет `chatStatus`;
- остальные пункты записывают свой `chatStatus`.

После любого переключения:

- `url.hash` принудительно становится `#/chats`;
- затем вызывается `render()`.

### 71.7. Подсчет бейджей

Для верхнего `Pill` используются counts по scope:

- `mine`
- `groups`
- `external`

В интерфейсе бейджи у верхнего `Pill` скрыты и не рендерятся.

Для нижнего `Topline` используются counts по status внутри `mine`:

- `new`
- `active`
- `completed`

Для экрана `Заявки` используются counts по status внутри `requests`:

- `new`
- `active`
- `completed`

Если count = 0, бейдж соответствующего пункта скрывается.

### 71.8. Данные списка

Список строится через `getChatThreadsForSelection(scope, status)`.

Mapping:

- `mine + new` -> `mine/new`
- `mine + active` -> `mine/active`
- `mine + completed` -> `mine/completed`
- `groups` -> `groups/*`
- `external` -> `external/*`
- `requests` -> `requests/*`

### 71.9. Строка чата

Строка чата рендерится через `renderChatListItem(thread)` на базе `renderRow(...)`.

Состав строки:

- avatar или photo слева;
- `title`;
- `preview` как subtitle;
- `timeLabel` справа;
- `unread` как badge;
- trailing mode `chat-meta`.

Ссылка строки:

- `#/chat/<thread.id>?back=%23/chats`

### 71.9. Пустое состояние

Если `threads.length === 0`, показывается отдельный empty state:

- title: `Чатов пока нет`
- description: `Когда появятся новые переписки, они будут собраны в этом разделе.`

## 73. Связи между касаниями, звонками, чатами и анализом

## 74. Что важно не сломать в коммуникационных разделах

- `touch detail` и `chat detail` сейчас принципиально read-only и не содержат composer.
- meeting внутри touch detail живет по отдельной ветке: есть summary, но нет transcript.
- логика back-навигации у касаний завязана на query `back`, ее нельзя упрощать без проверки всех входов из клиента и задачи.
- `calls` и `chats` полностью зависят от `rmoFeaturesEnabled`; при выключенном флаге эти route должны оставаться недоступными.
- фильтры звонков и чатов живут в `window.location.search`, а не в hash query; это важно для совместимости со всеми текущими bind-функциями.

## 77. Экран `#/search`

### 77.1. Назначение

Поиск — это глобальный cross-entity экран, который ищет одновременно по:

- клиентам;
- задачам.

Он живет отдельным route и открывается:

- из tab bar;
- из кнопки поиска в шапке чатов;
- из режима tab bar `search-trailing`, когда RMO выключен.

### 77.2. Параметры маршрута

Экран использует query-параметры в hash:

- `q`
- `scope`
- `back`

Текущее значение поиска берется через `getSearchQueryFromHash()`.

Поддержка `scope` в хелперах есть, но текущий экран всегда рендерит:

- `renderSearchResults("all", query)`

Это значит, что в текущей версии UI не дает выбрать только клиентов или только задачи.

### 77.3. Header

Header экрана симметричный и статичный:

- слева hidden placeholder;
- title `Поиск`;
- справа hidden placeholder.

Back-button на текущем экране отсутствует.

### 77.4. Поле поиска

Экран всегда рендерит `renderSearchField(...)` с placeholder:

- `Имя, компания, задача...`

После рендера `bindSearchApp()` автоматически:

- фокусирует input;
- ставит курсор в конец строки.

### 77.5. Поведение ввода

На каждый `input`:

- локально обновляется query в hash через `updateHashParams(...)`;
- если строка непустая, устанавливается `q=<value>`;
- если строка пустая, параметр `q` удаляется;
- параметр `back`, если он уже был, сохраняется.

После обновления URL экран не перерисовывается целиком, а только:

- пересчитывает результаты;
- локально обновляет DOM блока результатов.

### 77.6. Clear button

Кнопка очистки:

- скрыта при пустом запросе;
- показывается, когда строка поиска непустая.

По клику:

- поле очищается;
- `q` удаляется из hash query;
- `back` сохраняется;
- блок результатов возвращается в исходное состояние;
- input снова получает focus.

### 77.7. Состояния поиска

Экран имеет три состояния.

#### Подсказка до ввода

Если запрос пустой, показывается только prompt:

- `Введите имя, компанию, телефон, email или другие данные, чтобы быстро найти нужное.`

#### Ничего не найдено

Если запрос есть, но результатов нет:

- title: `Ничего не найдено`
- description: `Попробуйте сократить запрос или проверить написание имени, компании или задачи.`

#### Есть результаты

Если найдены совпадения:

- сначала показывается секция `КЛИЕНТЫ`, если есть client results;
- затем секция `ЗАДАЧИ`, если есть task results.

### 77.8. Что входит в поиск по клиентам

`getClientSearchResults(query)` ищет по:

- `client.name`
- `client.company`
- `client.phone`
- `client.email`
- `client.description`
- текстовому названию статуса клиента
- summary description клиента
- summary price клиента
- всем контактам клиента
- всем касаниям клиента:
  - `touch.title`
  - `touch.subtitle`
  - `touch.time`

### 77.9. Что входит в поиск по задачам

`getTaskSearchResults(query)` ищет по:

- `model.title`
- `model.description`
- `model.time`
- `task.status.label`
- текстовому названию типа задачи
- данным связанного клиента:
  - имя
  - компания
  - телефон
  - email
  - статус

### 77.10. Результаты по клиентам

Строка клиента в поиске показывает:

- `name`
- subtitle по приоритету:
  - `company`
  - `phone`
  - `email`
  - `Без компании`
- badge статуса, если он есть

Переход:

- `#/clients/<clientId>`

### 77.11. Результаты по задачам

Строка задачи в поиске показывает:

- title задачи;
- отформатированное время как subtitle;
- иконку типа задачи;
- chevron.

Переход:

- `#/task/<taskId>`

## 83. Что важно не сломать в поиске, настройках и дайджесте

- `#/settings` — это два разных продукта в одном route, переключаемые через `rmoFeaturesEnabled`.
- смена языка через settings сразу перерисовывает все приложение и влияет на каждый экран через DOM-localization.
- developer settings меняют реальную структуру навигации и доступность route, это не декоративный экран.
- поиск ищет глубоко, включая касания и summary клиента, поэтому любые новые поля нужно решать: индексировать их или нет.
- дайджест строится не из отдельной сущности, а из derived-агрегатов задач и клиентов; правки логики задач сразу меняют digest.

## 86. Глобальные переходы состояния приложения

### 86.1. Корневые продуктовые фазы

На верхнем уровне приложение живет в одной из фаз:

1. splash
2. onboarding
3. auth
4. setup
5. post-login permissions
6. main product

Переходы между ними происходят не через единый state machine объект, а через сочетание:

- `window.location.hash`
- `auth state`
- `authFlow state`
- `settings.rmoFeaturesEnabled`
- внутренних route guard-ов в `render()`

### 86.2. Переход из splash в onboarding

Если hash пустой:

- сначала показывается splash;
- после таймера происходит `render()`;
- затем route по умолчанию становится onboarding.

### 86.3. Переход из onboarding в auth

Онбординг не сохраняет флаг completion.

Переход выполняется только навигацией:

- `Далее`
- `Начать работу`
- `Пропустить`

Все эти действия в итоге приводят пользователя на `#/login`.

### 86.4. Переход из auth в setup или product

После успешного входа/регистрации/восстановления:

- auth state становится авторизованным;
- дальше пользователь переводится либо в setup flow, либо в main product flow, в зависимости от сценария.

### 86.5. Переход из setup в продукт

После завершения setup пользователь попадает в продуктовую часть.

Если пользователь уже авторизован и вручную открывает `#/setup`, route guard в `render()` переводит его на:

- `#/clients`

### 86.6. Post-login permissions как промежуточный слой

После логина приложение может показать последовательные permission prompts.

Это не отдельный route, а overlay-state поверх продуктового рендера.

Порядок фиксирован:

1. `notifications`
2. `contacts`
3. `whatsapp`

Одновременно на экране может существовать только один такой prompt.

## 88. Инварианты данных между разделами

### 88.1. Клиент — центральная сущность

Большинство экранов завязано на `clientId`.

От клиента зависят:

- карточка клиента;
- касания;
- задачи клиента;
- результаты звонка;
- поиск;
- дайджест;
- настройки приватных клиентов;
- call/chat analysis.

Любая поломка соответствия `task.clientId` или `touch.clientId` приводит к разрыву нескольких экранов сразу.

### 88.2. Задача наследует критичные данные через клиента

Во многих местах задача не самодостаточна.

Она подтягивает:

- имя клиента;
- статус клиента;
- контактные данные клиента;
- визуальные приоритеты;
- наличие телефона;
- историю касаний.

Это значит, что изменение клиента мгновенно меняет:

- task detail;
- поиск задач;
- дайджест;
- call results;
- доступность call/message action.

### 88.3. Касания влияют сразу на несколько зон

Новое касание после сохранения или анализа влияет минимум на:

- клиентский timeline;
- task detail;
- pending touch notice;
- detail screen касания;
- поиск по клиентам;
- analysis flow.

### 88.4. Дайджест — derived view, не отдельная база

Утренний дайджест ничего не хранит отдельно.

Он целиком пересобирается из:

- task cards;
- клиентских статусов;
- derived period logic;
- отсутствия активных задач.

Следствие:

- изменение одной задачи может поменять сразу несколько блоков дайджеста;
- изменение статуса клиента может повлиять на hot agenda;
- удаление клиента или задачи меняет дайджест без отдельной синхронизации.

## 89. Обязательные поля и их системные последствия

### 89.1. Создание клиента

Для нового клиента обязательны:

- `lastName`
- `phone`

Пока они не заполнены:

- submit disabled;
- карточка не может быть сохранена.

Следствие:

- любой созданный вручную клиент в системе гарантированно имеет телефон;
- call/message action для таких клиентов потенциально доступны сразу.

### 89.2. Редактирование клиента

Редактирование использует ту же валидацию обязательных полей:

- `lastName`
- `phone`

Это защищает уже существующие карточки от сохранения в неполном виде.

### 89.3. Создание задачи

Для новой задачи обязательны:

- `title`
- `client`
- `type`

Если хотя бы одно значение пустое:

- submit остается disabled.

### 89.4. Редактирование задачи

Для редактирования задачи обязательным считается только:

- `title`

Остальные поля могут остаться в предыдущем значении.

### 89.5. Auth-flow

Обязательность по auth-flow распределена по шагам:

- phone-step требует номер;
- code-step требует полный код;
- password-step требует валидный пароль и подтверждение.

Проблема на любом шаге блокирует переход к следующему.

## 90. Сохранение, перерисовка и side effects

### 90.1. Общий паттерн

В приложении почти все мутации работают по шаблону:

1. прочитать текущий state из localStorage
2. применить patch или пересобрать массив
3. сохранить в localStorage
4. либо сделать `render()`, либо сменить `window.location.hash`

### 90.2. Полный route-transition после действий

Через `window.location.hash` завершаются:

- создание клиента;
- редактирование клиента;
- создание задачи;
- редактирование задачи;
- login/logout;
- переходы onboarding/auth/setup;
- переходы из call results;
- переходы из dialer/calls/chats/touches.

### 90.3. Локальное DOM-обновление без полного render

Без полного route render сейчас живут отдельные механики:

- поиск;
- часть glass select/picker сценариев;
- modal/sheet состояния;
- некоторые interaction flow внутри detail-экранов.

### 90.4. Локализация как обязательный post-render шаг

После каждого полного `render()` обязательно выполняется:

- `localizeApp()`

При точечных DOM-вставках используется:

- `localizeElementTree(node)`

Следствие:

- новые DOM-фрагменты, созданные в runtime, нужно локализовать вручную;
- пропуск этого шага дает mixed-language интерфейс.

### 90.5. Empty viewport lock

После полного render синхронизируется:

- `syncEmptyViewportLock()`

Это влияет на layout пустых экранов и требует осторожности при добавлении новых empty states.

## 91. Критичные сценарии удаления и изменения сущностей

### 91.1. Удаление клиента

`deleteClient(clientId)` влияет сразу на несколько storage-слоев.

При удалении клиента происходит:

- удаление из `createdClients`
- удаление созданных задач этого клиента
- удаление client overrides
- удаление task overrides, связанных с клиентом
- очистка pending touches клиента

Это один из самых сильных side-effect сценариев в приложении.

### 91.2. Удаление задачи

`deleteTask(taskId)`:

- удаляет задачу из created tasks;
- чистит overrides;
- добавляет `taskId` в deleted state, если это нужно бизнес-логике конкретной задачи.

Изменения сразу влияют на:

- списки задач;
- client detail;
- дайджест;
- поиск;
- call results suggestions.

### 91.3. Complete / reopen задачи

`completeTask(taskId)` и `reopenTask(taskId)` не меняют отдельный boolean-флаг.

Они меняют:

- поле `time`

А весь остальной UI уже выводит статус из него.

Следствие:

- формат строк времени нельзя менять без проверки completed logic;
- period classification жестко связана с текстом времени.

## 93. Сводка системных инвариантов

Ниже — краткий список правил, которые должны оставаться истинными для корректной работы продукта.

- У клиента, созданного вручную, всегда есть телефон.
- `clientId` — главный ключ связности между клиентами, задачами, касаниями и результатами анализа.
- Завершенность задачи определяется не отдельным флагом, а значением поля времени.
- Все новые runtime DOM-вставки должны проходить через локализацию.
- `rmoFeaturesEnabled` меняет не внешний вид, а саму карту доступных разделов.
- Поиск должен учитывать актуальные derived-данные, а не только seed-поля.
- Дайджест всегда должен пересчитываться из актуальных задач и клиентов без ручной синхронизации.
- Pending touches должны исчезать после успешного анализа.
- `call results` — это продолжение task/client workflow, а не изолированный аналитический экран.
- Developer settings могут менять поведение продукта и должны рассматриваться как рабочий инструмент конфигурации.

## 94. Итог покрытия документа

На этом этапе документ покрывает:

- карту маршрутов;
- глобальные состояния и storage;
- onboarding, auth, setup, permissions;
- доменные сущности;
- контакты, задачи, call results;
- касания, звонки, чаты;
- поиск, настройки, developer settings, дайджест;
- cross-screen зависимости;
- feature flags;
- системные инварианты.
